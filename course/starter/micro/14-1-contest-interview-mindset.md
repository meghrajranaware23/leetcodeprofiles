## Part 1 — Contest & Interview Mindset

### 1. Why timers feel different

Contests and interviews have clocks. Beginners skip reading when the timer starts. Strong beginners **compress** each step — they don't delete steps.

### 2. The skill in one sentence

> **0–2 read · 2–4 plan · 4–15 code · 15–18 debug · 18–20 submit or log stuck point.**

### 3. 20-Minute Timed Workflow

```
0–2 min   Read + edge cases
2–4 min   Paper plan
4–15 min  Code + test examples
15–18 min Fix WA / debug
18–20 min Submit or log stuck point
```

### 4. Stack matching preview (Valid Parens #20)


### 5. What strong timed solvers do

| Weak habit | Strong habit |
|---|---|
| Panic at 10 min — skip read step | Read + edge cases in first 2 min |
| Submit without testing examples | Run Examples 1–2 before Submit |
| Forget stack empty check on Valid Parens | Trace `"(]"` — mismatch on `]` |
| Treat timer as "code faster" | Timer as "same process, tighter pace" |

### 6. The key insight

> **Process under timer beats panic** — interviewers care that you read, plan, and debug systematically, not that you type fastest.

### 7. Common Day 14 mistakes

| Mistake | Fix |
|---|---|
| Panicked when timer hit 10 min — skipped read step | First 2 min = read only |
| Submitted without testing examples under time | Run visible examples at 15 min |
| Forgot stack empty check on Valid Parens | End: stack must be empty |
| Rushed Add Binary carry without tracing | Trace `"11" + "1"` on paper |
